# Spec: First Character Creation

**Slug:** `06-first-character-creation`
**Status:** Draft
**Author:** Human + Claude
**Date:** 2026-11-12

## 1. Summary

This feature lets the player create their first character inside the "Configure Match" menu (the
placeholder shell introduced by `02-initial-screen`): pick a class (Fighter, Wizard, or Thief, default
Fighter), see the character's eight Sistema Daemon attributes generated by dice roll and distributed
according to the chosen class's archetype, and pick a weapon. The character (class, attributes, weapon)
is stored in Pinia so a future feature can hand it to the already-existing battle scene
(`05-combat-scene`). This US covers only generation and display — it does not wire the created character
into any battle yet.

## 2. Daemon System grounding

| Mechanic | Rules reference section | Notes on how it's used here |
| --- | --- | --- |
| Eight attributes (`FR`, `AGI`, `DEX`, `CON`, `INT`, `WILL`, `PER`, `CAR`) | §2 Attributes | Attribute codes, names, and roles (Strength, Agility, Dexterity, Constitution, Intelligence, Willpower, Perception, Charisma) are taken verbatim from the reference's table; this feature only adds a generation method and a per-class distribution rule on top. |
| `d6` die | §1 Core resolution mechanic / `04-dice-rolling-system`'s fixed `Dice` set | The "4d6 drop lowest" roll is built from four `d6` entries via the existing `DieRoll` primitive; no new die type is introduced. |
| Weapon catalog (`WEAPONRY`) | `03-weapon-list-seeding` | The weapon select reads from the already-seeded `WEAPONRY` SQLite table; this feature adds the first query/composable that reads it, since `03-weapon-list-seeding` explicitly left that consumption for later. |

**Intentional deviation:** Sistema Daemon's official character-creation step (§9, step 3) allocates
attributes by distributing a fixed campaign point pool (e.g. 101 points for a Realistic/Horror campaign)
across the 5–18 range, not by rolling dice. Per the human's explicit instruction, this US does **not**
use that official point-buy method at all — attributes are generated purely by "roll 4d6 drop the lowest
die, nine times, drop the lowest total" (a classic "ability score" method from other systems), giving
each of the 8 attributes a value in the 3–18 range. This is a conscious, explicitly approved deviation
under the Golden Rule (§14) for this spike, not an oversight, and no attempt is made to reconcile the
resulting values with the official point-buy budget.

## 3. Goal and value

- **Goal:** validate that the prototype can generate a playable, class-flavored character — attributes
  and a weapon — through a simple player-facing flow, as the first concrete step toward populating the
  existing battle scene with a real player-controlled unit instead of placeholder/hardcoded data.
- **Value:** gives the human a first character to look at and sanity-check (does a Fighter actually
  "feel" physically strong, does a Wizard "feel" mentally strong) before any combat math consumes these
  numbers, and produces the first reusable "generate and store a character" building block for future
  character-creation or multi-unit features.

## 4. Scope

### In scope

- A Pinia store (or an extension of the existing scene-related state) holding the current character's
  class, its 8 attribute values (keyed by `FR`, `AGI`, `DEX`, `CON`, `INT`, `WILL`, `PER`, `CAR`), and the
  selected weapon.
- A `CharacterClass` type/enum: `fighter`, `wizard`, `thief`.
- A pure attribute-generation function in `src/utils/`: roll `4d6` (via the existing `DieRoll`/`d6` from
  `04-dice-rolling-system`), drop the lowest of the four dice, sum the remaining three; repeat 9 times;
  drop the lowest of the 9 totals; return the remaining 8 values.
- A pure per-class distribution function in `src/utils/` that takes the 8 rolled values and a
  `CharacterClass`, and returns the 8 values assigned to attribute codes according to that class's
  archetype (§5), randomizing which specific value lands on which attribute within each tier.
- Clicking "Start" on the main menu: rolls a brand-new set of 8 attribute values, resets the class to
  `fighter`, applies the Fighter distribution, and stores the result in Pinia, before showing "Configure
  Match".
- The "Configure Match" menu now shows, instead of the "Coming soon" placeholder:
  - A class select (Fighter / Wizard / Thief, defaulting to whatever class is currently stored —
    `fighter` right after Start).
  - The 8 attributes, each with its English name, a short English description (translated from the
    reference's role column), and its current numeric value.
  - A weapon select populated from the `WEAPONRY` table (all weapons, no class filtering), defaulting to
    the first weapon returned by the query.
  - A new query/composable that reads all rows from `WEAPONRY` (the first consumer of that table, per
    `03-weapon-list-seeding`'s explicit deferral).
- Changing the class select re-runs the per-class distribution function on the **same already-rolled** 8
  values (no new dice roll) and updates the displayed attributes and the Pinia store accordingly.
- Changing the weapon select updates the stored weapon in Pinia.
- "Back" still returns to the main menu as before (per `02-initial-screen`); the stored character is not
  cleared by Back, but is overwritten by the next Start press's new roll.

### Out of scope

- Any use of the created character inside `05-combat-scene` (spawning it, rendering its sprite, running
  combat with its stats) — deferred to a future US. This US only stores the character in Pinia so that
  future work has something to read.
- The official Sistema Daemon point-buy attribute method (see §2's deviation) and any campaign-type
  configuration (Realistic/Horror, Adventure/Fantasy, etc.).
- Skills, Hit Points, Heroic Points, Protection Index, Enhancements, or any other derived statistic from
  §3/§4/§10 of the rules reference.
- A dedicated "Reroll" button inside "Configure Match" — rerolling is only possible via Back, then Start
  again.
- Any class filtering of the weapon list (e.g. restricting Wizards from heavy weapons).
- Character background, name input, portrait, or any other character-creation step beyond class,
  attributes, and weapon.
- Persisting the character across a page reload (consistent with `02-initial-screen`'s existing
  no-persistence behavior).
- Multiple characters, a party, or NPC/enemy character generation.

## 5. Functional requirements

1. Attribute generation: roll four `d6`, discard the lowest single die, sum the remaining three; repeat
   this nine times to get nine totals (each in the 3–18 range); discard the lowest of the nine totals;
   the remaining eight totals are the character's raw attribute pool.
2. Attribute codes and English names/descriptions, taken from the rules reference:
   - `FR` — Strength: measures a character's physical power.
   - `AGI` — Agility: measures a character's whole-body agility.
   - `DEX` — Dexterity: measures a character's manual dexterity.
   - `CON` — Constitution: measures a character's vigor and physical resistance.
   - `INT` — Intelligence: measures learning speed and mental power — the "strength" of magic.
   - `WILL` — Willpower: the power to resist magic and mental attacks.
   - `PER` — Perception: measures the ability to notice the surrounding environment.
   - `CAR` — Charisma: the power to persuade NPCs.
3. Per-class distribution of the 8 rolled values onto the 8 attribute codes:
   - **Fighter:** the 4 highest of the 8 rolled values are assigned, in random order, to `FR`, `AGI`,
     `DEX`, `CON`; the 4 lowest are assigned, in random order, to `INT`, `WILL`, `PER`, `CAR`.
   - **Wizard:** the 2 highest of the 8 rolled values are assigned, in random order, to `INT` and `WILL`;
     the 2 lowest are assigned, in random order, to `PER` and `CAR`; the 4 remaining (middle) values are
     assigned, in random order, to `FR`, `AGI`, `DEX`, `CON`.
   - **Thief:** the 3 highest of the 8 rolled values are assigned, in random order, to `AGI`, `DEX`,
     `INT`; the 5 remaining values are assigned, in random order, to `FR`, `CON`, `WILL`, `PER`, `CAR`.
4. Clicking "Start" on the main menu always performs a fresh roll (requirement 1), resets the class to
   `fighter`, applies the Fighter distribution (requirement 3), stores the result in Pinia, and then
   navigates to "Configure Match" — mirroring `02-initial-screen`'s existing Start behavior, now with
   this extra side effect.
5. "Configure Match" renders: a class select (options Fighter/Wizard/Thief, bound to the stored class), a
   list of the 8 attributes (name, description, value), and a weapon select (options loaded from
   `WEAPONRY`, bound to the stored weapon).
6. Changing the class select applies the new class's distribution function (requirement 3) to the
   existing 8 rolled values (no new roll), updates the Pinia store, and the displayed attribute values
   update immediately.
7. Changing the weapon select updates the stored weapon in Pinia; no other state changes.
8. The weapon select's options are every row currently in `WEAPONRY`, queried through a new composable/
   query function; the initially selected weapon is the first one returned by that query.
9. "Back" returns to the main menu without clearing or modifying the stored character.

## 6. Non-functional requirements

- State: the character (class, 8 attribute values, selected weapon) lives in a Pinia store — data only,
  mutated through actions — per CLAUDE.md's state/logic split.
- Logic: the dice-rolling and per-class distribution algorithms are pure functions in `src/utils/`
  (framework-agnostic, no Pixi/Pinia/Vue/GSAP dependency), reusing the `DieRoll`/`d6` primitive from
  `04-dice-rolling-system`, and are covered by Vitest unit tests, consistent with CLAUDE.md's testing
  scope (pure combat/formula logic in `src/utils/` is the one area expected to carry automated tests).
- Rendering: the "Configure Match" menu stays plain Vue + Tailwind (DOM), consistent with
  `02-initial-screen`'s decision to keep this screen outside Pixi.
- UI text/labels: English, consistent with the rest of the initial-screen UI (`02-initial-screen` already
  uses "Turn Based Prototype", "Configure Match", etc.) and with CLAUDE.md's language policy.
- Data access: the weapon select reads `WEAPONRY` through a new read-only query/composable built on the
  existing `sql.js` setup from `03-weapon-list-seeding` — no new database engine or schema change.
- Randomization within each class's value-to-attribute assignment (requirement 3) must use a fair random
  shuffle, not a fixed or biased order, so repeated rolls visibly vary which specific attribute gets which
  value within its tier.

## 7. Edge cases

| Edge case | Expected behavior |
| --- | --- |
| Two or more of the 9 totals tie for lowest when discarding | Any one of the tied lowest totals may be discarded (no special tie-breaking rule needed) — the remaining 8 values are still a valid pool. |
| Two or more of the 8 rolled values are numerically equal | Both are kept and can both be assigned within the same or different tiers; equal values are not deduplicated. |
| Switching class back and forth repeatedly (Fighter → Wizard → Thief → Fighter) | Each switch re-runs that class's distribution on the same 8-value pool; the random shuffle means the exact attribute layout for a given class is not guaranteed to be identical across switches, which is expected. |
| `WEAPONRY` query returns zero rows (e.g. database not seeded) | The weapon select renders empty with no selection and no stored weapon; this is a known degraded state the player must `npm run db:seed` to resolve — not a crash. |
| Clicking Start repeatedly without visiting "Configure Match" in between | Each click re-rolls and overwrites the previously stored character; only the latest roll is kept. |
| Navigating Back then Start again | Produces an entirely new roll (requirement 4) — the previous character is discarded, matching the "fresh roll per Start" decision. |

## 8. Risks and mitigations

| Risk | Likelihood/Impact | Mitigation |
| --- | --- | --- |
| The dice-based attribute method (3–18, no campaign point budget) produces attribute spreads that feel very different from a "balanced" Daemon character once real combat math is layered on | Low/Low | Accepted and documented as an explicit, human-approved deviation (§2); this is a spike validating the character-creation flow, not final game balance. |
| `WEAPONRY` has no existing query/composable (per `03-weapon-list-seeding`'s explicit deferral), so this US must build the first one, with no established pattern to follow | Medium/Low | Keep the new query function minimal (read-only, "select all weapons") so it is trivial to review and does not block on bigger data-access architecture decisions. |
| Randomized tier assignment could, by bad luck in a small sample, look non-random to the human during manual testing (e.g. always landing the same visual order) | Low/Low | Use a standard array-shuffle algorithm (e.g. Fisher–Yates) and verify with a few repeated Start/class-switch cycles during manual testing. |

## 9. Dependencies

- Depends on `02-initial-screen` (the "Configure Match" placeholder menu and the Start/Back navigation
  this feature extends).
- Depends on `04-dice-rolling-system` (`Dice`/`DieRoll`, specifically `d6`) for the attribute rolls.
- Depends on `03-weapon-list-seeding` (the seeded `WEAPONRY` table) for the weapon select; this feature
  adds the first query/composable reading that table.
- Blocks, conceptually, a future US that connects the stored character to `05-combat-scene` — but does
  not implement that connection itself.

## 10. Definition of Done

- [ ] Clicking "Start" generates a fresh 8-value attribute pool (4d6 drop-lowest, 9 rolls, drop worst
      total), resets the class to Fighter, applies the Fighter distribution, stores everything in Pinia,
      and opens "Configure Match".
- [ ] "Configure Match" shows a class select (Fighter/Wizard/Thief), the 8 attributes with English
      name + description + current value, and a weapon select populated from `WEAPONRY`.
- [ ] Selecting a different class re-distributes the same 8 rolled values per that class's rule (§5.3)
      without rolling new dice, and the displayed values update accordingly.
- [ ] Selecting a different weapon updates the stored selection; no attribute values change.
- [ ] Fighter distribution always puts the 4 highest rolled values on `FR`/`AGI`/`DEX`/`CON` and the 4
      lowest on `INT`/`WILL`/`PER`/`CAR`, in randomized order within each group.
- [ ] Wizard distribution always puts the 2 highest rolled values on `INT`/`WILL`, the 2 lowest on
      `PER`/`CAR`, and the remaining 4 on `FR`/`AGI`/`DEX`/`CON`, all randomized within their group.
- [ ] Thief distribution always puts the 3 highest rolled values on `AGI`/`DEX`/`INT` and the remaining 5
      on `FR`/`CON`/`WILL`/`PER`/`CAR`, all randomized within their group.
- [ ] "Back" returns to the main menu without clearing the stored character.
- [ ] The dice-rolling and per-class distribution functions live in `src/utils/`, are pure, and have
      passing Vitest coverage for: the 4d6-drop-lowest roll's value range, the 9-rolls/drop-worst
      selection, and each class's tier assignment.
- [ ] `npm run lint` and the Vitest suite both pass.
- [ ] All code, identifiers, comments, and UI text are in English, per CLAUDE.md's language policy.

## 11. Manual verification plan

1. Run `npm run db:reset && npm run db:seed` (if not already seeded) so `WEAPONRY` has data, then
   `npm run dev` and open the app.
2. Click "Start": confirm "Configure Match" opens showing the class select defaulted to "Fighter", 8
   attributes with plausible 3–18 values, and a weapon select with a weapon already chosen.
3. Confirm the 4 attributes `FR`/`AGI`/`DEX`/`CON` show the 4 highest of the displayed values and
   `INT`/`WILL`/`PER`/`CAR` show the 4 lowest (compare the numbers directly).
4. Switch the class select to "Wizard": confirm `INT`/`WILL` now show the 2 highest values and
   `PER`/`CAR` the 2 lowest, using the same 8 numbers as before switching (no new values appear).
5. Switch to "Thief": confirm `AGI`/`DEX`/`INT` show the 3 highest values, still from the same pool.
6. Switch back to "Fighter" a couple of times: confirm the specific attribute-to-value mapping within
   each tier visibly varies between switches (randomization is actually happening), while the physical/
   mental grouping rule itself never breaks.
7. Change the weapon select to a different weapon: confirm the attribute values are unaffected.
8. Click "Back", then "Start" again: confirm a brand-new set of 8 attribute values appears (different
   from step 2's roll — rerun a few times if needed to be confident it's re-rolling, not caching).
9. Run `npx vitest run` and confirm the new attribute-generation and distribution tests pass.
